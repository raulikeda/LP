    Projeto de Compilador - Linguagens & Paradigmas - 2026/1

    Este projeto é dividido em múltiplos roteiros, onde construiremos um compilador funcional passo a passo. Cada roteiro corresponde a uma versão do compilador com novas funcionalidades.

    Atenção

    Só é considerado entrega válida no prazo se o código houver passado em todos os testes do servidor!

    Montando o Ambiente

    Existem duas linguagens a serem definidas, uma é a linguagem que o compilador será desenvolvido e é de livre escolha sua (ver o Hall da Fama abaixo). A segunda é a linguagem alvo do compilador (linguagem compilada), e é única para toda a turma e definido coletivamente.

    Para início do projeto, você deve montar um ambiente de desenvolvimento adequado:

    • Escolher uma linguagem orientada a objetos, com recursão e com dicionários.
    • Se você optou por Python, criar um arquivo main.py para o início do programa.
    • Se você optar por uma linguagem diferente do Python, avise o professor.
    • Criar um repositório privado no GitHub
    • Instalar o Compiler Tester App no repositório
    • Um badge das entregas deverá aparecer no README do seu repositório

    Atenção

    Se o repositório for renomeado, é preciso reinstalar o App no repositório!

    Esse repositório será usado para realizar as entregas do semestre. Qualquer alteração nas configurações do repositório (por exemplo no nome) precisa ser notificado.

    Você irá criar tags para realizar as entregas e elas serão corrigidas automaticamente. Cada roteiro possui uma versão diferente e a tag seguirá o modelo: vX.Y.Z onde:

    • X é o major build - dado pelo roteiro
    • Y é o minor build - dado pelo roteiro
    • Z é o patch build - incremental a medida que novas tags são lançadas e controladas pelo desenvolvedor.

    Logo o fluxo de trabalho será:

    • O roteiro alvo indicará a versão v0.0
    • A primeira tag a ser feita será a versão mais o patch: v0.0.0
    • Se não houver erros (sinalizados por issues), roteiro finalizado
    • Se houver erros, corrigí-los e realizar uma nova tag (v0.0.1, v0.0.2, ... e assim sucessivamente)

    Troubleshooting:

    • Se o badge não sinalizar algo e não houver issues, é possível que a tag está incorreta.
    • Atenção ao padrão (utilizar v minúsculo no início)
    • Se você testou localmente e está correto, verifique se você deu push no seu código e utilizou aspas na entrada

    Importante 1

    A entrega só é considerada válida se houver passado em todos os testes. Se você enviar, não passar e ultrapassar a hora limite, será a entrega será considerada atrasada. Não deixe para enviar em cima da hora!

    Importante 2

    Não é necessário versionar o código com nomes de arquivos ou diretórios (por exemplo: diretório Roteiro1 ou main_v0.0.py). Todo o versionamento é feito automaticamente com as tags. Sobrescreva o arquivo atual sem dor no coração.

    Enviando uma Tag

    Atenção

    Antes de enviar uma tag, não se esqueça de realizar commit e push para o repositório remoto!

    Para realizar a entrega do código da versão atual, você deve enviar um tag para o repositório remoto. É necessário acrescentar uma tag e realizar um push específico.

    No exemplo abaixo, um roteiro implementa a versão 0.1.x do compilador, utiliza-se os seguintes comandos: 

    # Apenas depois de ter dado push no seu código!
$ git tag v0.1.0
$ git push origin v0.1.1

    Só é possível colocar uma tag apenas uma vez, portanto solte a tag apenas quando houver finalizado. Caso precise soltar uma correção, utilize um incremento no número do patch, por exemplo v0.1.2, v0.1.3, etc.

    Também é possível realizar tags utilizando releases no website, porém é pouco produtivo.

    Verificação Sintática

    Além da verificação semântica (análise dos resultados da implementação), também há uma verificação sintática do código. Isso significa que você deve seguir as especificações designadas nos roteiros em termos de nomenclatura, propriedades e estilo idiomático de programação.

    Em Python, por exemplo, é preciso que os métodos sigam a formatação snake_case (apesar dos roteiros apontar o padrão camelCase). Ou ainda, as classes devem conter os atributos e métodos exatos na especificação, incluindo algumas propriedades, como estático.

    Extra Credit

    Todos os roteiros a partir da versão v1.0 possuem um exercício extra valendo pontuação adicional na nota de compilador da disciplina. Os execícios extras utilizam uma tag com prefixo 'xX.X'. Por exemplo, o exercício extra da versão v1.0 será x1.0.

    Você não deve carregar as modificações para o próximo roteiro porque pode interferir na correção sintática. É aconselhável implementar os exercícios em uma branch separada.

    Ver a pontuação de cada exercício nos slides da Aula 01 no Blackboard.
